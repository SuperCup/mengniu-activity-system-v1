# 确认清单与功能逻辑核查

核查日期：2026-10-21。核查对象为当前 `hq-console/` 多文件工程；`docs/` 中原始 V5 HTML 作为历史材料，不作为当前运行入口。此次未修改业务代码。

结论：标黄内容大多有对应界面，但不能认定已满足验收条件。即使按可交互原型验收，也存在计划归属丢失、导入流程中断、二维码串页和统计不一致等明确错误。项目提交、审批、页面生成等主要动作尚未形成可执行闭环。

## 二、功能逻辑问题

以下 P1 表示阻断主要流程或导致业务数据错误，P2 表示局部功能错误。已知演示占位与可复现错误分别说明。

### F01 — P1：提交和审批没有更新业务状态（已知占位）

- 位置：`hq-console/js/pages/project-create.js:77`、`project-approve.js:45`、`project-manage.js:160`。
- `submitProject()`、`projApprove()`、`projAct()` 仅弹提示；不创建项目，也不更新状态。保存项目草稿按钮无处理。
- 实测：提交前后项目均为7条；对待审批项目点同意后仍为 `pending`。输入不存在的 PO 也提示提交成功。
- 影响：无法完成“创建→审批通过→补充计划→推送”链路；撤回、终止、删除、复制及重发/复制链接同样是提示占位。
- 修正：最少实现原型内真实状态变更、必填及 PO 有效性校验，重绘相关列表；外部发送能力应单独接入并以结果反馈成功。

### F02 — P1：新计划不保存项目归属

- 位置：`hq-console/js/components/plan-drawer.js:137`、`:158`；项目过滤在 `hq-console/js/pages/plan-batch.js:24`。
- 新对象没有 `proj` 字段，`openPlanNew()` 的标题也固定为“双节常温奶满减”。初始数据脚本只在加载时为已有数据赋默认项目，不会处理随后新增的计划。
- 实测：从项目进入创建计划，保存成功但 `proj` 为空，`planScoped()` 不包含新计划，即从当前项目列表消失。
- 修正：新建时要求明确项目并保存项目ID；全部计划入口应提供项目选择；标题和默认日期随项目变化。

### F03 — P1：导入后无法继续编辑计划

- 位置：`hq-console/js/core/drawer.js:27`、`hq-console/js/components/import-drawer.js:206`、`plan-drawer.js:33`。
- 打开导入抽屉会关闭计划抽屉；导入完成仅关闭导入抽屉，不恢复计划抽屉。再次点击“创建计划”会重置 `PN.ret/sku`。
- 实测：导入3条门店后没有打开的抽屉；重新创建时门店数回到0。
- 影响：正常界面操作无法连贯完成“导入门店→导入商品→保存计划”。计划主列表还缺少编辑入口，已有计划明细也不能正常补改。
- 修正：维护抽屉返回上下文，导入完成/取消时恢复原计划草稿；补全计划列表编辑入口。

### F04 — P1：审批、终止及创建人条件没有实际限制

- 位置：`hq-console/js/pages/plan-batch.js:38`、`:86`，`components/plan-drawer.js:14`、`:125`，`components/batch-drawer.js:99`。
- 项目状态仅生成提示，创建计划按钮一直可用，保存函数不校验审批状态、终止状态及操作者归属。
- 实测：待审批项目可打开创建入口并保存计划。
- 修正：按钮和保存处理均校验状态与身份；已终止项目及不满足权限的操作者只能查看。

### F05 — P1：计划与批次数值校验缺失

- 位置：`hq-console/js/components/plan-drawer.js:125`、`batch-drawer.js:125`。
- 计划预算、数量、面额、门槛未检查有限值、正数、整数、金额关系和项目预算余额；`pnNum()` 还会把非数值内容转换为0。
- 批次数量只判断大于0，单日上限只判断不能高于总上限，单人数量只判断区间。
- 实测：计划保存了预算 `-1`、数量 `1.5`、面额 `-2`；批次保存了总数量 `1.5`、单日上限 `-2`、单人 `1.5` 张。
- 修正：在保存端执行明确的金额/整数规则、预算和日期范围约束；不要只依赖 HTML 的 min/max。

### F06 — P1：批次可重复绑定，并被本地保存直接标为已审核

- 位置：`hq-console/js/components/batch-drawer.js:139`；`plan-list.js:10`。
- 未检查批次号是否已被其他计划占用。未填外部批次号时自动制造 `WX...` 编号，并统一设置 `bstat='已审核'`；列表据此显示通过，领券页把它当成可建页批次。
- 实测：第二个计划可以保存与第一个计划完全相同的 `23020101`。
- 影响：不满足严格一一对应；尚未真实创建/审核的批次也可能进入后续领券配置。
- 修正：批次号全局唯一、归属不可冲突；区分“信息草稿/待提报/外部审核通过”，依据真实回填或明确演示状态推进。

### F07 — P1：编辑批次会覆盖原计划，破坏金额口径

- 位置：`hq-console/js/components/batch-drawer.js:135`。
- `p.face/p.thr/p.qty` 被批次表单直接覆盖，但 `budget/coupon/mech/used/usedAmt` 等数据没有同步校验或版本处理。
- 实测：计划原面额15、数量9000、预算135000；保存批次后面额10、数量1.5，预算仍135000，历史核销6320仍保留。
- 修正：计划与执行批次各自保留字段；已有核销时限制关键字段变更，差异必须明确处理。

### F08 — P1：二维码编号跨领券页重复

- 位置：`hq-console/js/components/qr-drawer.js:70`、`:205`。
- `qrCodeName()` 忽略参数 `key`，固定活动ID；序号按每个页面的每个渠道重新计数。
- 实测：r1和r2的首张线下码，链接不同，编号均为 `MN-WX-202612-0041-OFF-01`。
- 影响：物料对账、二维码回溯无法唯一定位。两位序号截断还会在数量增长时再次冲突。
- 修正：以真实活动为基础分配唯一编号，活动内统一序号或纳入页面ID，明确超过99枚时的规则。

### F09 — P1：打开无二维码的渠道会串用上一页链接

- 位置：`hq-console/js/components/qr-drawer.js:75`、`:158`、`:197`。
- `qrPickCode()` 查不到码时直接返回；`openQr()` 未清理旧图与链接，`qrBlank()` 也不清除 `qrCur.item`。
- 实测：先打开r1物料码，再打开r2公众号（该渠道无码），右侧仍显示r1链接；切换空渠道后复制动作仍可读取旧码。
- 修正：打开页面或进入空渠道时清空选中码、图、链接，禁用复制/下载，选码必须核对当前页面与渠道。

### F10 — P1：二维码和领券页面生成尚为占位

- 位置：`hq-console/js/components/qr-drawer.js:21`、`:234`；`hq-console/js/pages/coupon-page.js:460`、`:520`。
- 码图由随机种子绘制点阵，没有编码目标URL；下载仅提示。建页、保存、停用、删草稿按钮只调用 `closeDrawer()`，不更新 `PAGES/QRDATA`。
- 影响：已有演示渠道可增列表记录，但不能完成新活动生成可分发二维码的业务要求。
- 修正：接入真正二维码编码、文件生成及领券页数据增删改，渠道统计应来自对应码的真实事件。

### F11 — P1：看板指标、渠道明细无法对账（含演示数据设计问题）

- 位置：`hq-console/js/pages/dashboard.js:20`、`:134`、`:174`、`:331`。
- 销售额为优惠金额乘固定10.7，非实付订单汇总；发券数量取 `bqty`（发放上限），再按 `DB_CHAN.share/rate` 分摊，不读取二维码领取与核销。
- 实测：核心核销数12428，渠道核销合计10462，相差1966。趋势、零售商、商品等图表另用固定数据；同比环比也固定。
- 筛选输入无事件，查询/重置未绑定处理；未找到所说明的活动→计划→批次→二维码下钻控件及联动。
- 修正：采用同一份订单/领取数据按筛选范围聚合，核对分项之和；取得呼市/河南正式口径与参考后再逐指标验收。

### F12 — P1：登录与权限尚未构成访问控制（已知演示占位）

- 位置：`hq-console/index.html:11`、`login.html:110`、`js/core/router.js:41`、`:63`、`js/pages/system-admin.js:97`。
- 登录只写本地标志，没有真实扫码认证；`nologin` 可直接跳过。角色配置更新数组后不参与菜单渲染、路由准入或数据范围过滤，也没有当前登录用户与角色映射。
- 所有9个注册菜单均被渲染，包括系统管理与服务商页。服务商页关于令牌、过期和预算隐藏也仅是文案，页面本身还展示核销预算。
- 修正：用可信身份和用户角色映射驱动菜单、操作和数据访问控制；服务商入口单独验证令牌及范围。真实集成依赖蒙牛提供对接文档。

### F13 — P2：无表头导入会丢弃合法记录

- 位置：`hq-console/js/components/import-drawer.js:120`、`:126`。
- 小于2行直接返回；首行含“门店/商品/零售商/69码”任何字样就视为表头，没有比对完整列名。
- 实测：粘贴单条合法门店记录解析为0条；粘贴2条且首条店名含“门店”时只保留第二条。
- 修正：允许1行无表头；仅在完整表头匹配时跳过首行。CSV 引号转义等格式也应使用标准解析器处理。

### F14 — P2：服务商“唯一联系人”的数据与编辑联动不完整

- 位置：`hq-console/js/data/vendors.js:9`、`pages/project-create.js:10`、`components/vendor-drawer.js:54`。
- 初始联系人数量为3/2/1/2/2，界面只是统一取首条，不能证明数据层唯一；保存既有服务商会把其他联系人丢弃。
- `vsSave()` 调用 `initProjVendor()` 后固定选中索引1，覆盖业务正在创建项目时选中的服务商。
- 实测：项目先选索引0，编辑另一家服务商保存后变成索引1。
- 修正：明确迁移为唯一联系人数据，保留并恢复当前所选服务商，只刷新对应联系人。

### F15 — P2：带小数金额格式错误

- 位置：`hq-console/js/core/format.js:19`。
- 实测 `money(123.45)` 返回 `¥123.45.00`。
- 修正：使用带 `minimumFractionDigits/maximumFractionDigits:2` 的数值格式化，不再拼接 `.00`。

## 三、验证范围及限制

- 静态检查当前32个 JavaScript 文件的语法，均通过。
- 使用独立无头 Chrome 打开实际 `file://` 入口，页面挂载9个视图；本轮探查没有捕获未处理页面异常。
- 执行14组浏览器探查，记录业务状态、字段和处理结果。带表头的门店/商品示例各解析3条且无校验错误；选择服务商可正常展示首个联系人。语法及加载成功不代表业务流程正确。
- 复现脚本：`_analysis/review-20261021.cjs`；原始结果：`_analysis/review-20261021-results.json`。探查仅修改独立浏览器会话内存，未改动业务源文件。
- 仓库没有提供微信支付后台对应版本的字段/规则基准、呼市/河南正式确认口径，以及钉钉标准对接文档。因此不能对这些外部一致性与真实对接给出通过结论；本次未执行微信支付或钉钉真实联调。
- 本轮为代码和关键业务路径核查，不覆盖所有视口、视觉规范、所有文件编码/CSV变体或生产安全测试。

## 四、建议修复顺序

1. 先修计划归属、导入返回上下文，补计划编辑入口和保存时状态限制，使原型可走通。
2. 再补项目状态变化、数量金额预算校验、批次唯一性及状态管理，避免成功提示掩盖数据错误。
3. 修二维码唯一编号、空渠道串页及页面生成保存；统一看板数据来源并实现筛选。
4. 根据正式资料验收微信批次字段、呼市/河南看板；钉钉认证与权限作为明确集成任务跟进。
