一

一期范围与边界

把微信支付一条业务链跑通​

1.1 一期整体流程​

① 活动创建业务/区域提报，含预算、PO、商户号、服务商、机制附件
② 内部审批固定线性流程，同意/驳回，无财务节点
③ 邮件推送服务商审批通过即签发活动 ID，邮件发出活动链接
④ 服务商确认执行打开链接确认接单，免登录
⑤ 上传计划计划 ID 自定义，按模板填写，金额不超预算
⑥ 上传批次批次 ID 与计划 ID 一一对应
⑦ 创建领券 H5选批次建页面，一活动多页面，出链接与二维码
⑧ 数据分析发券-领取-核销分析 + 核销订单看板
一句话概括：一期解决「活动审批流程对接、服务商能关联、券计划与实际批次对接、发券H5页面落地、数据同步」。这条链跑通，二期的多平台扩张和会员体系对接才有基础。

1.2 券规则与机制信息的边界（本期确认口径）​

事项由谁负责本期口径
项目级总预算平台管理统一按核销口径；作为计划上传的金额上限，计划金额合计不得超出
券类型 / 面额 / 门槛 / 发放量 / 单人限领 / 券有效期服务商配券时确定由服务商在微信支付后台按活动机制配置；平台不预设、不做券规则校验，计划与批次回传后原样展示
机制 / 规则 / SKU / 零售商等说明文件客户自行上传项目创建时以附件形式上传（多文件、多类型），随活动流转给服务商下载；平台只承载与归档，不解析内容
小程序 / 公众号 / 商户号客户提供用于领券 H5 落地与发券链路；商户号同时对应零售商（门店）归属的填报字段
二

六大需求与功能映射

本期确认需求，分别落在哪些模块​

#需求实现方式承载模块
1 蒙牛创建活动审批后，邮件推送活动链接给服务商 审批终审通过即触发四步联动：签发活动 ID → 生成活动级令牌链接 → 渲染邮件模板（活动名称/周期/预算/交付要求/机制附件）→ 发送至服务商联系人邮箱。邮件发送记录、失败重发、已读回执均落库。 项目审批 项目管理 工作台
2 服务商在邮件链接确认执行和回传数据 服务商无需账号、无需登录，凭邮件内一次性令牌打开活动操作页：确认执行（或拒绝并填写原因）→ 确认后页面解锁上传区。令牌与活动 ID 绑定、可设有效期、活动终止即回收。 服务商协同
3 服务商把微信支付计划上传到对应活动，计划 ID 自定义，字段按模板 活动页提供计划模板下载（xlsx，带字段说明与示例值）；服务商按模板填写后上传，计划 ID 由服务商自定义并在系统内做唯一性校验（活动内唯一）。上传即校验：表头一致、金额合计 ≤ 项目核销预算。券面额与门槛由服务商配券时确定，平台不做券规则校验。 计划管理
4 批次数据上传须与计划 ID 一一对应 批次模板回传批次 ID + 计划 ID（微信支付推送的批次信息可一并带入）。系统校验：每条计划必须有且仅有一个批次、批次不得重复绑定、不得存在无计划的孤儿批次。不满足则整批拒绝并输出差异清单，支持仅重传失败行。 批次管理
5 业务/区域看到服务商配置的批次，在活动中选批次创建领券 H5，一活动多页面，产出链接与二维码，H5 与神策对接收数，分析发券-领取-核销 批次列表对业务侧可见（按数据权限收窄）；在活动详情内「新建领券页面」→ 勾选一个或多个批次 → 选模板/换背景图 → 生成移动端领券页，输出短链与二维码（可下载多种尺寸）。神策埋点上报曝光、PV/UV、领取点击；分析页按发券 → 领取 → 核销三层出数与转化率。 领券 H5 数据看板
6 核销订单数据单独看板，支持时间、活动、创建业务部门筛选 独立菜单入口，按六块分析组织：①核心指标五张卡（核销订单数/销售额/优惠金额/笔单价/ROI，带同比环比）②销售额·优惠金额·订单数三条日趋势曲线 ③发券渠道环形图与明细表 ④零售商 TOP10 ⑤商品 TOP10 ⑥时段分析（7×24 热力图 + 周内占比）。筛选条件：核销时间区间、活动、创建业务部门，可组合。一期不做订单导出。数据源为微信支付核销回调与订单拉取。 数据看板 微信支付对接
需求 3、4 的关键设计决策：计划 ID 由服务商自定义而非系统下发，是本次会议明确的口径——系统不做计划编码规则，只做唯一性与对应关系校验。这降低了服务商的改造成本，但要求批次回传必须带计划 ID，否则无法建立对应关系。这一条直接写入公司标准计划/批次模板的字段规范，作为服务商对接的硬约束。
券规则与机制信息不在平台预设（本期确认口径）：平台只管理「项目级总预算 + 计划与批次的对应关系」，不预设券类型、面额、门槛与有效期，券的具体规则由服务商在微信支付后台按活动机制配置。机制、规则、SKU、零售商等说明文件由客户在项目创建时自行以附件形式上传至平台，平台只做承载与归档、随活动流转给服务商，不解析附件内容、不据此做业务校验。

功能项功能说明

M02
项目创建

活动提报入口，平台锁定微信支付；含预算、PO、商户号、服务商选择与机制附件上传

8 项
功能项功能说明
活动基本信息活动名称、活动目标、活动周期、适用范围、活动负责人与联系方式；投放平台锁定微信支付。不填写券类型/面额/门槛/发放量/单人限领/券有效期（券规则由服务商配券时确定）
预算与费用科目预算金额（核销口径）、预算来源、费用科目、承担主体；预算从上游系统取值的接口预留，无接口时手工填写
PO 单号填写 PO 单号作为准入与结单校验依据；无 PO 不允许提交
商户号填报项目级填报多个微信支付商户号，作为准入必填项（区域提报易漏填）。计划层的零售商按商户粒度选取：从零售商库按零售商名称筛选 → 勾选具体商户添加（一个商户对应一个微信支付商户号），字段为微信商户号 / 区域 / 商户名称 / SG 零售商，支持全选与按计划分别维护
服务商选择从服务商清单中选择承接方，校验其承接平台包含微信支付；带出联系人与邮箱（邮件推送目标）
提交前预校验三项校验：必填完整性、预算额度是否超池、服务商承接能力；不做券规则与券有效期校验（券规则不在本平台）
草稿与提交审批草稿保存/编辑/删除；提交后生成项目单号并进入审批流，字段锁定
机制附件上传客户在项目创建时自行上传机制、规则、SKU、零售商等说明文件：支持多文件批量上传，格式 pdf / doc / docx / xls / xlsx / ppt / pptx / 图片 / zip，单文件 ≤20MB；按类型打标（活动机制 / 规则说明 / SKU 清单 / 零售商清单 / 其他）；支持预览、下载、删除，提交审批后锁定不可删改；附件随审批详情、活动详情展示，对服务商操作页可见可下载。平台只承载与归档，不解析附件内容、不据此做校验
M03
项目审批

固定线性流程，同意/驳回；通过即触发自动联动

5 项
功能项功能说明
待审批列表状态树切片：待我审批 / 我发起的 / 已审批；多维查询（单号、BU、金额区间、提报时间）
审批详情四段式：项目概况、活动规划、预算与 PO、服务商信息；核心区展示批次计划表（计划名 / 机制 / 起止时间 / 零售商 / 活动商品 / 预算分配），作为审批判断依据——计划金额合计 ≤ 核销预算、零售商为已落库商户号、商品为商品库具体 SKU；金额高亮。审批页不展示机制附件与审批轨迹
审批操作同意 / 驳回（驳回必填原因）；固定线性流程，不做加签、转办、代理，一期只保留同意与驳回两个动作
审批留痕各节点审批人、时间、意见在后台全量留痕、可追溯；一期不在审批页面向审批人展示轨迹视图，需要时在活动详情内查看。审批页仅保留同意 / 驳回两个动作，不设撤回后重审的轨迹界面
审批通过自动联动四步连动：签发活动 ID → 生成活动级令牌链接 → 渲染邮件 → 置为「待推送服务商」，并推送待办给业务
M04
项目管理

活动台账与全生命周期，含推送、终止与活动 ID 管理

5 项
功能项功能说明
活动台账与状态树六态：草稿（含被驳回）、待审批、待推送服务商、待服务商确认、执行中、已终止；「待传计划 / 待传批次 / 待建页面」作为执行中的进度标识与筛选条件，不单独设状态；计划数、批次数、页面数按计数展示，不设「已配置」「已生成页面」子状态；不设归档状态。状态字典见 7.2
活动详情全量信息 + 审批留痕 + 推送记录 + 服务商确认状态 + 计划与批次（含对应关系与校验结果）+ 领券页面 + 数据摘要。机制附件在项目创建与活动详情内查看，审批页不再单独呈现附件区
推送服务商发送活动链接邮件，记录推送时间、接收邮箱、发送结果；支持重发与更换收件人
活动 ID 管理活动主 ID 签发、平台子 ID 派生、券批次 ID 绑定
活动终止批次未产生前可终止；终止后邮件通知服务商停止执行、回收令牌链接、释放额度；不支持变更
M05
服务商协同

免登录令牌链接；确认执行 + 上传入口

5 项
功能项功能说明
免登录令牌链接按活动签发访问令牌，与活动 ID 绑定；可设有效期、可停用；活动终止即回收。令牌泄露风险以「仅可见本人活动、只读+上传」收敛
邮件模板与发送邮件含活动名称、周期、预算、交付要求、机制附件（链接页内下载）与操作链接；模板可维护，发送前预览
服务商确认执行链接页内「确认执行」或「无法承接并填写原因」；结果实时回写活动状态并通知业务
服务商操作页四步：确认执行 → 上传计划 → 上传批次（按计划 1:1）→ 等待业务方建页；含模板下载、历史回传记录、逐段校验结果反馈；每步校验通过才解锁下一步。批次上传下方另设「同步核销订单」入口：按批次回传订单明细，须含批次编码、一条订单只归属一个批次，校验通过后进入核销分析；移动端适配
状态回写与提醒确认/拒绝、计划已传、批次已传三类状态回写；工作台以待办与消息条数如实呈现停留时长，不提供催办动作（一期已确认不做催办），业务按需自行重发邮件或终止
M06
计划管理

计划 ID 自定义，模板化上传，金额与规则校验

5 项

六

端到端业务主流程

系统上线后，一条微信支付活动怎么走完

① 提报
业务或区域在「项目创建」填活动信息、核销预算、PO 单号、商户号，选择承接服务商，上传机制 / 规则 / SKU / 零售商等说明附件 → 提交，三项预校验通过后进入审批。
② 审批
管理员/审批人在「项目审批」同意或驳回（驳回填原因）。同意即自动签发活动 ID、生成令牌链接、渲染邮件，活动置为「待推送服务商」。
③ 推送
业务点击「推送服务商」，邮件带活动链接发出；服务商联系人邮箱收到，无需账号。
④ 确认
服务商打开链接 → 确认执行（或拒绝并说明）。确认后活动进入「执行中」，链接页解锁上传区。
⑤ 传计划
服务商在链接页下载机制附件、计划模板 → 按模板填写、计划 ID 自定义 → 上传。系统校验表头、计划 ID 唯一、金额合计不超核销预算（超预算整批拒绝）；通过后生成计划记录。
⑥ 传批次
服务商在微信支付后台配好券 → 按计划逐条回传批次（批次 ID + 计划 ID）→ 系统做一一对应校验，批次数须等于计划数，通过后批次状态为「已审核」。
随后服务商按批次同步核销订单（订单须带批次编码，一条订单只归属一个批次），平台校验无孤儿订单、无重复归属。
⑦ 建页面
业务在活动详情看到批次 → 新建领券页面、勾选批次、选模板/换背景 → 生成 H5 与二维码，下载用于物料印刷。一个活动可建多个页面，同一批次只能挂在一个启用中的页面上；页面启用中可停用、改名、换背景，不可改批次组合（链接已铺出去，改组合会造成消费者看到的券与物料不一致），要换组合需新建页面并停用旧页面。
⑧ 看数据
消费者扫码领券 → 神策回收曝光与行为数据、微信支付回收核销数据 → 「活动分析」看发券-领取-核销转化，「核销订单看板」按时间/活动/业务部门查订单。
⑨ 终止
批次未产生前可终止：终止后停发券、回收链接、通知服务商、释放预算额度；数据留存，按「已终止」状态查询，不设归档态。
九个环节里有三个是本次新增的核心增量：③ 邮件推送（原来靠人工通知）、⑤⑥ 计划与批次的结构化回传（原来靠微信或邮件传 Excel，无校验、无对应关系）、⑦ 领券页面自助生成（原来需要外部开发页面）。这三段是把「线下协同」变成「系统协同」的关键。

7.2 活动状态字典​

活动状态统一为 6 个状态 + 3 个进度标识。状态只回答「活动卡在谁那里」，即当前由哪一方推进；「做到哪一步」由进度标识表达。两类信息分开，避免同一件事在状态、工作台、列表三处各说一遍。

状态含义可执行动作责任人
草稿（含被驳回）已创建未提交；被驳回后回此状态，保留驳回原因编辑、上传/替换附件、提交审批（预校验通过后可用）、删除草稿提报人
待审批已提交，审批流中审批人：同意、驳回；提报人：撤回（撤回后回草稿，需重新提交）。一期不提供催办能力审批人
待推送服务商审批已通过，活动 ID 与链接已签发，邮件未发出推送（发送邮件）、更换推送对象、终止活动提报人 / 业务运营
待服务商确认邮件已送达，服务商尚未确认重发邮件、复制确认链接、终止活动。一期不提供催办服务商能力；服务商长期未确认时由业务判断重发或终止服务商
执行中服务商已确认；按进度标识推进终止活动；建领券页面；换页/停用页面服务商 / 业务运营
已终止已终止且链接已回收，不可再变更只读查看、终止记录、复制为新项目—
进度标识（仅存在于「执行中」，不参与状态流转）：① 待传计划（服务商已确认、无有效计划）② 待传批次（已有计划、存在未绑定批次的计划）③ 待建页面（批次已齐、未建领券页）。标识由系统按数据自动计算，用于工作台待办与项目管理筛选，不再另设活动状态；计划数 / 批次数 / 页面数以计数展示，不设「已配置」「已生成页面」子状态。
三层归属关系（项目 → 计划 → 批次 → 页面），不能跨层挂靠： 项目是唯一归属主体。一个项目可有多条计划，一条计划对应且仅对应一个批次（1:1，计划数恒等于批次数），一个批次最多挂在一个启用中的领券页面上；领券页面只能组合本项目下的批次，不能跨项目取券。
  • 计划与批次：上传时即绑定活动 ID，与当前项目不一致则整批拒绝；列表按项目聚合，每行带项目号，详情带项目上下文。页面顶部不设状态流程条，只展示计划 / 批次明细（计划表带「对应批次」列，批次表带「对应计划」列）。
  • 核销订单：订单必须带批次编码，按批次归属到计划；一条订单只能归属一个批次，不允许孤儿订单。平台以批次为最小统计单位，核销数据按批次 → 计划 → 项目逐层汇总。
  • 领券页面：入口是「先选项目 → 再在项目内建页面」，新建走右侧抽屉（基础信息 → 选批次 → 外观与渠道 → 预览与生成），与列表分离；页面列表带所属项目列。
  • 终止：只作用于项目层。批次一旦产生即不可终止、不可变更；终止后所属页面的二维码全部失效。
与之配套的三条规则：① 被驳回后回到「草稿」，凭驳回原因与版本号区分是初次创建还是重新提交；② 「已终止」为终态，已终止活动按时间筛选查询，不另设归档状态；③ 工作台不设「待终止/归档」统计卡，统计卡只对应可执行动作。
