# 项目与计划流程优化：可直接交给 deepseek-harness / Cursor 的提示词

请在当前仓库实际完成下述前端原型优化，交付可运行、可回归的实现。不要只返回设计建议。先阅读本文件和 `docs/代码核查报告_20261021.md`，检查当前实现后再修改。

## 1. 项目范围与约束

- 当前运行入口为 `hq-console/index.html` 与 `login.html`。业务页面在 `hq-console/js/pages/`，共享抽屉在 `js/components/`，数据在 `js/data/`。
- 保持中文、现有视觉变量与页面风格，保持经典 script 及 file:// 双击运行能力。本轮不改造成新框架，不引入构建工具或必须依赖服务器的加载方式。
- 本轮核心：①报批时让审批人知道具体要做什么；②审批后提交人找到原计划，按微信产品类型补齐执行配置。修复这两条链路依赖的既有逻辑错误。
- 不扩大为整个看板重做、真实钉钉接入或真实微信建活动。外部接口与邮件要有适配边界；本地演示可真实更新本地数据，但不得把本地操作提示为外部创建/发送成功。
- 同时支持项目、审批、计划、待办、执行配置之间的联动，不能只改文案或抽屉样式。
- 所有下述流程为本项目推荐产品设计，不是微信平台规定；微信字段和限制以第8节来源为准。

## 2. 核心方案：同一计划分两阶段完善

流程：

创建项目与计划摘要 → 提交审批并冻结审批快照 → 审批通过 → 原提交人补充原计划执行配置 → 校验完成 → 推送服务商 → 服务商确认/外部建活动与回填 → 核验状态 → 执行。

报批阶段就生成稳定的 projectId 和 planId。审批通过后继续编辑同一个 planId，不复制计划、不重新创建、不按数组下标建立关联。项目与计划的编号、用户可见名称保持贯通。

项目是预算、组织、负责人和服务商的管理容器；计划是具体活动方案及其微信执行配置。一个项目允许多个计划；一个执行计划对应一个明确的微信产品类型及一份外部活动/批次绑定。不同优惠类型、不同门槛/面额、不同核销范围或需独立创建的时段应拆为不同计划，不把多个外部活动塞进一个模糊机制字符串。

不要在“创建计划”和“补充批次”中重复维护同一组面额、门槛、日期。计划业务方案、微信执行配置、外部创建结果分层保存，并在页面中清晰关联。

## 3. 报批阶段：业务方案必须足够明确

创建页分为“项目基本信息”“计划方案”“预算汇总”“审批预览”，不是要求用户先填完全部微信后台表单。

项目报批字段：项目名称、业务目标、业务部门、负责人及联系方式、项目周期、有效 PO/预算来源、可用预算、服务商及唯一联系人/邮箱、目标客群与区域渠道范围。

至少一条计划摘要；每条包含：

- 固定计划ID、计划名称、执行负责人（默认提交人）、活动类型及全场/单品范围。
- 结构化优惠方案：满减门槛/面额，或随机立减区间，或折扣比例及单笔优惠封顶，随类型显示。
- 计划周期、零售商/区域业务范围、全场或指定商品的业务范围说明。
- 目标用户、预计规模、计划预算上限；发券数量或参与次数按活动类型填写。不是所有类型都叫“发券数量”。
- 营销经费模式、业务出资承担方、叠加优惠政策等影响资金或优惠力度的条件。

报批阶段不强迫导入最终门店/SKU清单，不强迫填写外部批次号、准确商户授权、品牌素材、技术跳转参数等。已知的执行字段可提前填并在审批后保留，未知项显示“审批后补充”，不得使用演示默认值冒充真实输入。

审批详情应展示项目与每条计划的完整摘要、预算分配和风险提示。例如：“计划PL-001；代金券；常温奶满99减15；华东永辉指定门店；计划预算13.5万元；预计9000张；12月20—27日；每人2张”。审批人能够判断做什么、在哪做、给谁、何时做、最多花多少。

审批人看到的是提交时的只读快照，而不是随时变化的编辑草稿。提交与审批必须真正更新本地业务状态和相关列表。

## 4. 审批后：有明确入口找到原计划

1. 工作台增加“待我补充执行配置”，统计当前用户负责且已批准、未完成配置的计划；点击后展示这些原计划。
2. 项目管理的已批准项目显示“待补配置 x/y”，主按钮“继续完善计划”；进入该项目的计划列表。
3. 项目详情“计划”页签保留原计划ID、方案摘要、配置状态、缺失项和“继续配置”。
4. 全部计划列表按项目、计划名称/ID、活动类型、配置状态、负责人筛选。显示项目归属；全局创建时必须先选可操作项目。
5. 支持 `#v-plan?projectId=...&planId=...&tab=config` 或等效可恢复的路由。刷新后仍能定位该计划，不能丢失作用域。

补参编辑页顶部固定展示“审批已通过的方案”，下方是执行配置；不需要反复切页查原始审批。

分组为“基础与优惠规则”“商户及商品”“参与/领取限制”“展示与说明”“校验与服务商交接”。显示每组缺失项和来源，不用无意义的总百分比替代条件检查。

每个分组可保存草稿。允许配置不完整时保存；只有全部适用必填项和业务约束通过后才允许“配置完成”。取消、返回、刷新重进均不丢失已保存内容。

门店和商品继续使用导入。导入完成/取消返回当前计划编辑页并保留整个草稿。允许带表头和不带表头的单行或多行数据，正确处理CSV引号，逐行报告错误与重复；不要通过包含“门店/商品”等字样猜测表头。

## 5. 状态、版本和变更规则

区分三个维度，不要用一个 state 同时表示审批、配置和微信状态：

- 项目审批：草稿/审批中/已通过/已驳回/已撤回；可以兼容现有项目状态，但职责要明确。
- 计划配置：待完善/完善中/校验通过。就绪状态由字段和约束实时推导，不能只存一个可失真的百分比。
- 执行：待交接/待服务商确认/待外部创建/已创建待激活/运行中/暂停/结束/终止。外部状态和本地交接状态分别保存。

推荐兼容现有 PROJECTS 的生命周期，保留 draft/pending/approved/confirmed/running/stopped，批准后的“待补参/可推送”作为派生子状态。驳回结果单独留痕，不为迁就原枚举丢掉历史。

审批中锁定本次提交版本；撤回后才可修改重提。已批准后，优惠类型/力度、资金模式/承担方、预算上限、目标范围扩张、周期扩张、新增/删除计划及计划预算重新分配等关键修改，生成变更草稿和差异说明并重新审批。审批版本仍保留；有未批准的核心变更时不能把该变更下发执行。

审批后可直接补充的内容：审批范围内门店/SKU细化、合法商户号补齐、平台字段、素材和使用说明等；同样要留修改人和时间。若明细超出批准范围，应转变更审批。无法通过零售商/地区映射自动核验时，显式要求核验结果，不把任意导入当成范围内。

草稿、审批中、终止项目不得创建或修改执行配置；前端入口和保存动作都要校验。已通过后由执行负责人配置，必要时允许明确的管理员代办并留痕。模拟用户/角色只用于演示，不声称生产权限隔离。

项目推送服务商的前置条件：本次交接包含的计划均已批准且配置就绪，预算合计合法；未就绪计划不能被悄悄遗漏。本轮默认整项目交接，不引入隐式的部分上线。

## 6. 微信执行表单：按类型动态显示

建立 schema 配置，至少包含 key、label、valueType、unit、requiredWhen、visibleWhen、validator、sourceUrl、sourceSection、verifiedAt、productType、creationChannel、accountCapability。区分微信必填、本系统业务必填、条件必填、可选、暂未核验，不把所有字段都加星。

基础类型支持全场代金券（固定面额）、全场定额立减、全场随机立减、全场折扣。为单品代金券与单品立减保留类型和单品字段扩展；在所需字段及当前账号能力未核验完成前，显示待核验和缺项，不允许它们被误判为可执行。不要直接复用“商家券”或“商品券”的规则到“代金券”。

下表为表单分组和已知字段范围，不是宣称所有字段对所有账号都必填。正式 requiredWhen 需在所选产品、创建入口及账号下核验。

| 分组 | 代金券 | 立减/折扣 |
| --- | --- | --- |
| 基础 | 批次名称、归属商户、营销经费模式 | 活动名称、营销经费模式、定额/随机/折扣类型 |
| 优惠 | 面额、门槛、可用起止与生效规则 | 定额减价与门槛；随机规则与预算；折扣比例、单笔优惠封顶与门槛 |
| 范围 | 可用商户、支付方式/支付产品、叠加规则、商品限制/订单优惠标记 | 活动商户、用户类型、支付方式/模式、叠加规则、订单优惠标记 |
| 数量/资金 | 发放总上限、总预算、每人限领、单日限制、安全防刷、扣款方式/出资方（适用时） | 优惠总数量、每人参与次数、预算控制、出资方与会员AppID（适用时） |
| 展示 | 使用须知、品牌信息、logo和跳转入口按能力配置 | 活动说明与支付展示按产品要求配置 |

浏览器实际已核验到“创建立减”的第一步：活动名称（页面提示9个字以内）、定额/随机立减、预充值/免充值、减价金额、使用门槛、可用时间，以及任意时段/规则日期/不规则日期三种时间规则。尚未在当前账号核验第二步和代金券页；不要声称已完整抄取当前后台。

金额统一内部使用整数分，输入/显示用元，数量使用整数；折扣统一内部比率并明确UI单位，如8折=支付80%，不能颠倒“折扣”与“减免百分比”。百分比、次数、张数和金额不能混用。

业务预算校验：计划预算分配合计不超过项目审批预算，执行成本上限不超过对应计划审批预算。固定券理论成本=面额×发放上限；随机立减按规则预算求和；折扣不能用券面额公式计算，按明确配置的总预算及封顶约束校验。若平台没有总预算控制，不要伪造平台字段；本系统业务预算单独保存，并计算保守最大责任或阻断待确认。

门店中的“核销商户号”、活动“归属商户号”、实际创建活动的账户、出资方分开维护。不要直接拿第一家门店商户号当归属商户。商户号存在不代表关系和授权通过；执行就绪校验需有相应状态。

导入商品条码不代表微信能够按单品核销。明确本系统69码/店内码、零售商商品编码和微信下单所需商品字段之间的映射及接入前提；单品活动必须核验下单上送单品能力，缺失时不能显示已具备单品执行能力。

代金券是先领后用，后续可配置领券页；立减/折扣无需领券，不应强迫绑定领券页或填写每人可领张数。相应入口使用“参与/核销活动”及次数指标；需要宣传二维码时跳转活动说明页，不假装发券。

2. 商户后台立减与折扣手册（页面标注2026-05-21更新）：
   https://pay.wechatpay.cn/doc/v3/institution/4019697953
3. 创建代金券批次 API（页面标注2024-10-31更新）：

4. 用户此前打开的立减后台地址：
   https://pay.weixin.qq.com/index.php/extend/mktcreatebatch/createBatch/2

关键核验结果：后台代金券手册可用期描述为最长365天，API文档为最长90天；API的单用户上限为60，不能用商家券的100张替代。后台操作手册与API参数含义、长度、能力开放范围并不完全相同。

因此，本轮以“服务商在商户后台人工建活动后回填”为默认交付方式；只实现对该入口已确认的规则。若开发API适配，另用API schema，包含调用方请求号等技术必填，由系统生成而非让业务人员填写。

不能确认的上限或必填条件集中登记到 `docs/微信执行字段待核验.md`，说明涉及类型、字段、候选规则、来源冲突、是否阻断执行。可继续完成确定的部分；受影响的计划允许保存草稿，但不得显示“已具备微信创建条件”。不要把所有未知字段统一当可选，也不要静默取最宽松或最严格规则。

不要为了看后续字段而提交真实活动、激活、扣款、充值或发送业务邮件。

## 9. 建议的数据结构

可按项目实际风格调整命名，但保持以下职责：

Project：id、ownerId、businessFields、budgetFen、workflowState、currentProposalVersion、approvedVersion。

Plan：id、projectId、assigneeId、proposal（类型/机制/日期/范围/预算等）、executionConfig（按类型结构化）、configurationVersion、updatedAt。

ApprovalSnapshot：projectId、version、不可变的项目与计划方案快照、提交/审批人、时间、结果、意见。

ExecutionBinding：planId、approvedVersion、交接版本、外部产品类型、创建商户、外部stockId/activityId、外部状态、核验记录。外部引用不能复用到不同计划。

Readiness：基于当前字段、审批版本和权限等条件动态计算；输出缺失字段/不合法值/未核验条件及定位动作。

AuditEvent：实体ID、动作、操作者、时间、版本和变更摘要。不要存真实账号凭证。

## 10. 交付与验收

先给出简短实现清单，然后执行代码改造。不要停在计划阶段。完成后提供修改文件、实际验证结果、已知外部依赖。

至少验证：

1. 创建项目与两条不同类型计划摘要，提交后审批人准确看见摘要及预算合计，执行字段未补不阻止报批。
2. 审批通过后工作台出现当前负责人的待补配置计划，点击进入原planId，刷新仍定位同一计划，所有审批前已填值保留。
3. 门店导入、返回、商品导入、返回、保存、重进后，草稿和值完整；单行无表头、店名含“门店”、带引号CSV均不丢行。
4. 不完整配置允许保存草稿；点击配置完成时精确列出缺失项并跳到对应字段。
5. 代金券、固定立减、随机立减、折扣的适用字段与校验不同；切换类型不把旧类型字段误计为新类型已填。
6. 未审批、非负责人、已终止项目不能通过界面或直接保存动作越权补参；演示身份切换可验证此规则。
