# 蒙牛活动管理平台 一期产品需求文档（客户确认与验收版）

## 一、文档说明与使用方式

### 1.1 文档目的

本文档用于与客户逐项确认**一期产品的功能实现、业务流程与功能细节逻辑**，并在一期开发完成后作为**验收依据**使用。文档中每一条功能需求（FR）都配有可判定的验收标准，验收时按「需求编号 → 功能表现 → 验收结论」逐条核对，避免以主观感受判定完成度。

本文档同时承担三项职责：

1. **范围确认书**：明确一期做什么、不做什么、哪些事项需客户书面确认后才落入范围。
2. **功能契约**：明确每个模块的页面、字段、校验、状态与异常处理，作为开发、测试、验收三方共用的唯一口径。
3. **验收基准**：明确验收通过标准、验收流程与时间窗，签署后作为一期交付的判定依据。

## 二、项目背景与一期目标

### 2.1 现状与问题

蒙牛券活动由各事业部、区域及经销商依据业务需要发起。当前活动发起的效率与执行效果，在很大程度上取决于各团队自身掌握的资源与经验：部分团队由服务商承接执行，部分团队依托平台后台自行配置，业务人员需在活动方案、券配置、门店与商户号、数据回收等环节之间投入大量协调工作。上述模式支撑了各事业部的日常营销开展，同时亦使业务侧承担了较多营销之外的协调性工作。随着参与团队与活动数量的增加，集团希望将相关能力沉淀为可复用的平台能力——为业务人员提供一套可自主使用的工作平台，并在此基础上统一协同过程与数据口径。对照该目标，现有协同方式在以下四个方面仍有提升空间：

1. 活动信息需分头传递。活动方案在业务侧以邮件、表格等方式流转，券批次由服务商在微信支付平台侧创建，两者的一致性依赖人工核对维系。出现配置偏差时（如方案为满 99 减 15、批次实际配置为满 99 减 10），通常至执行阶段方可发现，此时予以纠正，活动已进入执行期。对业务侧而言，同一事项需在不同对象之间重复说明与确认。
2. 基础信息需逐次重新收集。门店、微信商户号、商品明细分别由业务、服务商及平台侧各自维护，集团内部尚未建立统一的商户号库，业务人员每开展一档活动均需重新收集与核对。商户号由对方财务部门管理，一次获取完整存在客观难度。已有数据积累的团队可复用既有信息，新接手的团队则需从零开始，各团队的启动成本存在差异。
3. 执行进度依赖人工跟进。提报、审批、推送服务商、批次回传等环节的进展分散于邮件与即时沟通工具，业务人员需逐环节跟进方可掌握当前状态。出现问题时，定位环节与责任方需跨渠道回溯，处理周期较长。
4. 效果评估于事后进行，口径与时效受限。核销、订单及预算消耗数据分散于服务商与各平台侧，看板依赖人工拼接，各来源之间口径存在差异。预算消耗与发放异常以事后汇总提醒为主，业务侧难以在投放过程中及时干预。一档活动结束后，对其投入产出进行完整评估本身即需耗费较多工时。

上述四点的共性在于：业务侧缺少一套可自主发起、推进并查看结果的工作平台，集团侧亦因此缺少统一的协同过程与数据口径。一期由此切入，将「活动提报 → 审批 → 批次配置 → 服务商执行 → 数据回流」主链路线上化：一方面使业务人员可自主完成一档券活动的发起与规范执行，另一方面在过程中自然沉淀协同记录与业务数据，为集团层面的费用费效管控提供支撑——既保障业务侧可用、易用，亦支撑集团侧可视、可管。

### 2.2 一期目标

一期不做大而全的营销中台，只跑通**「活动创建 → 审批 → 批次配置 → 服务商执行 → 发券核销 → 数据回流」这一条主链路**，并在链路上沉淀可追溯的项目、计划、批次与数据台账。

具体目标四条：

1. 一个活动从提报到执行，全流程在系统内留下结构化记录，不再依赖邮件正文传递关键信息。
2. 计划与外部批次建立稳定的一对一对应关系，批次号全平台唯一，杜绝方案与批次错配。
3. 门店、商户号、商品形成统一主数据，活动明细通过模板导入并做行级校验。
4. 核销与订单数据按批次回流，看板可按「活动 → 计划 → 批次 → 渠道二维码」逐级下钻。

### 2.3 一期成功判据

| 编号 | 判据 | 口径 | 判定方式 |
| --- | --- | --- | --- |
| G-01 | 主链路可完整跑通 | 从新建项目到数据在看板呈现，全流程无需人工改库或线下补录 | UAT 用 1 个真实活动走通全流程 |
| G-02 | 计划与批次一一对应 | 验收时有效计划数 = 有效批次数，无孤立批次、无跨项目绑定 | 数据核对 |
| G-03 | 关键动作可追溯 | 提交、审批、推送、确认、回传、终止六类动作均有系统日志，日志含操作人、时间、对象编号 | 抽查 10 条日志 |
| G-04 | 数据可回流可对账 | 核销事件与账单数据可按批次入库，日终对账产出差异清单 | 用测试数据核对一轮 T+1 对账 |
| G-05 | 服务商可自助执行 | 服务商凭邮件链接完成确认、下载、回传、上传四步，无需我方人工介入 | 用真实服务商账号演练一次 |

> 说明：一期不承诺业务效果类指标（如核销率提升幅度）。上述判据均为「系统是否具备该能力」的判定，不含对营销效果的评价。

## 三、名词与业务对象

### 3.1 术语表

| 术语 | 定义 | 易混淆点 |
| --- | --- | --- |
| 项目 / 活动 | 一次营销活动的管理单元，一项目对应一个项目单号、一个活动周期、一个核销预算、一个服务商 | 与「计划」「批次」不是同义词，层级为 项目 > 计划 > 批次 |
| 计划 | 项目下的执行单元，一期按「计划1、计划2…」自动命名；一期一个计划只承载一种机制 | 计划名称不是券名称 |
| 批次 | 微信支付侧的一张券，一个计划对应一个批次，一一绑定 | 「批次号」由服务商在微信后台建券后回传，不由平台生成 |
| 券 | 消费者领取与核销的优惠凭证，一期为全场代金券 / 全场立减两类落地形态 | 券面额属于批次层字段，不在报批阶段填写 |
| 机制 | 优惠口径，一期只支持「满减」与「减至」两种类型 | 「机制类型」是枚举，「机制」是业务文案（如满 99 减 15） |
| 券成本 | 批次已核销单数 × 券面额，用于预算与看板口径 | 不等于销售额，也不等于平台支出 |
| 发券任务 | 一次向某个渠道小程序推送一批批次的动作记录，生成一个任务号 | 不是「配券」，平台不记录渠道侧配券状态 |
| 渠道 | 承接发券的小程序入口，一期为「会员服务中心」小程序；按线下物料 / 公众号 / 私域区分二维码渠道 | 「渠道小程序」与「二维码渠道」是两个维度，不要混用 |
| 回传 | 服务商或小程序方通过开放 API 将批次、核销、执行情况、账单数据写回平台 | 平台不主动向微信拉取订单（见 D-05） |
| 核销 | 消费者在门店使用券完成抵扣，产生核销事件与订单 | 核销事件需按「批次号 + 微信订单号」去重 |
| 就绪 / 校验通过 | 计划的批次必填信息完整且通过规则校验，具备推送服务商的条件 | 不等于微信侧已成功建券 |

### 3.2 业务对象与关系

| 对象 | 唯一标识 | 归属关系 | 关键约束 |
| --- | --- | --- | --- |
| 项目 | 项目单号（SO + 日期 + 序号）、活动 ID（MN-WX-年月-序号） | 归属创建组织 | 活动 ID 与项目单号全局唯一，创建后不可修改 |
| 计划 | 计划编号（PL-项目尾号-序号） | 属于唯一项目 | 审批前后沿用同一计划记录，不复制产生第二套 |
| 批次 | 外部批次号（6~20 位数字） | 属于唯一计划 | 批次号全平台唯一，一个计划最多绑定一个批次；未回传前允许为空 |
| 发券任务 | 任务号 | 属于唯一渠道 + 唯一项目 | 一次任务可包含该项目多个批次，任务号唯一 |
| 核销订单 | 微信订单号 | 属于唯一批次 | 必须携带有效批次号，否则进入待处理队列并告警 |
| 门店 | 门店 ID、微信商户号 | 平台级共享主数据 | 商户号 8~12 位数字且全局唯一 |
| 商品 | 69 码、店内码 | 平台级共享主数据 | 69 码与店内码至少填一个；同一店内码可对应多个零售商 |

### 3.3 层级与数量约束

1. 项目与计划为 1:N，计划与批次为 1:1，批次与核销订单为 1:N。
2. 批次未回传前，计划处于「待完善 / 完善中」，此时允许「计划数 > 批次数」；推送服务商前必须全部计划校验通过，验收时必须满足「有效计划数 = 有效批次数」。
3. 禁止出现无项目归属的计划、跨项目绑定的批次、重复绑定的批次号。
4. 商户号、批次号、门店 ID、69 码、店内码一律按**文本**存储与传输，禁止数值化，避免前导零丢失与科学计数法转换。

以下能力一期**不建设、不交付、不计入验收范围**。若客户需要，须按第十四章走变更流程，另行确认范围、工期与费用。

### 4.3 范围待定项

第十四章列出 10 项需客户书面确认的事项（D-01～D-10）。在客户确认前，本文档已按「我方默认口径」编写；确认结果若与默认口径不同，按变更流程调整，不视为我方漏做。

### 4.4 范围控制规则

1. 范围以本文件 4.1 / 4.2 为准，任何口头需求不构成范围。
2. 新增需求进入「后续版本池」，由双方评估后决定是否纳入本期；纳入须同时确认对工期与验收时间的影响。
3. 客户验收时不得以原型示意中的非本期内容（如计划变更页）作为缺项依据。

### 5.3 数据范围规则

1. 数据按创建组织归属：组织架构为「集团 → 事业部 → 区域 → 经销商」四级，业务运营可见本级及所有下级组织的数据。

### 5.4 服务商免登录访问

2. 令牌具备有效期（建议 7 天，待确认，见 D-07），过期后链接失效，需业务方在项目管理中「重发」。

4. 令牌失效、越权访问、重复提交均记录系统日志并返回明确提示。

### 7.3 关键流转的前置校验

**提交审批（草稿 / 未通过 → 审批中）**

1. 项目名称、活动负责人、联系方式、预算单号、核销预算、预算凭证、服务商、至少 1 名项目审批人必填。
2. 预算单号按所选预算系统校验；不存在或未审批直接拦截，并提示具体单号。
3. 预算数据及接口以实际对接结果为准。
4. 活动周期起止必填，开始日期不晚于结束日期。
5. 至少 1 个计划；每个计划的机制、机制类型、活动零售商明细（≥1 条）、活动商品明细（≥1 条）均完整。
6. 提交后生成 16 位项目编号并冻结本次报批方案快照；后续配置不覆盖原始报批信息。

**审批结果回写（审批中 → 已通过 / 未通过）**

1. 审批为并联审批，审批人之间无先后、无分级；所选审批人全部同意回写「已通过」，任一人未通过回写「未通过」。
2. BPM 回写每位审批人的结果、处理时间和审批意见；系统只读展示，不提供同意、驳回、撤回等审批动作。
3. 已通过后进入批次配置；未通过可编辑后重新提交，审批意见保留在项目详情时间轴。

**推送服务商（待推送 → 已推送）**

> 推送确认文案：请确认，与本项目配置名单中的零售商已达成合作，且已通知零售商打开单品回传操作。避免因名单信息错漏，或合作尚未达成、后续中止等原因产生消费者客诉，或其他数据披露风险。按钮为「暂不推送」和「确认推送」。

1. 项目下计划数大于 0。
2. 全部计划「校验通过」（见 7.4）；存在未完成计划时，拦截并列出未完成计划名称。
3. 推送前校验计划预算不超过项目核销预算。
4. 推送前展示合作及单品回传风险确认；取消不变更状态，确认后记录推送人、时间、计划及通知结果。正式通知失败不得误记成功。

**服务商确认（已推送 / 待确认 → 已确认）**

1. 令牌有效且未过期。
2. 项目仍处于已推送 / 待确认状态。
3. 确认后写入确认时间与确认人，项目进入已确认；批次回传入口开放。

**批次号回传（已确认 → 已配置）**

1. 批次号按全平台唯一校验，冲突行标红并拦截整批提交。
2. 校验通过后写入批次号与配置时间，项目进入已配置，等待服务商上传账单。

**开始执行（已配置 → 执行中）**

1. 服务商上传第 1 次账单后，项目进入执行中。
2. 执行中可查看计划与批次、挂券与配置、数据看板；终止后进入已结束，全部写操作关闭。

### 7.4 批次配置完整性

| 配置情况 | 判定 | 处理 |
| --- | --- | --- |
| 待补充 | 批次信息表单未填写（券名称、面额、门槛、时间、上限均空） | 计划行显示「补充配置」 |
| 存在缺项 | 表单已填但存在必填缺失或规则不通过 | 抽屉内提示缺失项，保存不通过 |
| 校验通过 | 全部必填完整、规则通过、零售商明细 ≥1 条 | 计划行显示「明细」，项目可推送 |

> 配置完整性不等于微信侧已建券或审核。计划列表按项目状态派生显示「待推送 / 已推送 / 待服务商确认 / 已确认 / 已配置 / 进行中 / 已结束 / 已中止」等汇总状态；筛选条提供待完善、待配置、进行中、已结束、已中止 5 个选项。

### 7.5 异常与终止

| 场景 | 处理 | 留痕 |
| --- | --- | --- |
| 审批未通过 | 项目进入未通过；可编辑后重新提交；审批意见由 BPM 回写 | 审批人、结果、时间及意见 |
| 周期结束 | 停止新增配置及投放，保留历史数据和已发生业务的回传对账 | 结束时间 |
| 通知失败 | 记录失败并按约定重试，不误记成功 | 对象及结果 |
| 超时未确认 | 已推送 / 待确认状态不变；卡片标红并支持重发 | 重发次数与时间 |
| 批次号冲突 | 回传时校验全平台唯一，冲突行标红并拦截整批提交 | 冲突批次号与占用方 |
| 终止 | 待推送、已推送、待确认、已确认、已配置、执行中可终止；终止后进入已结束，全部写操作关闭，释放未核销预算 | 终止时间、操作人 |
| 计划 / 项目删除 | 本期不提供删除项目或删除计划入口；已提交过的计划不可删除 | — |
| 历史数据 | 有效关联或核销记录不得直接覆盖 | 历史归属 |

### 9.5 导入通用规则

1. 模板列名固定，不允许增删列；表头匹配失败时提示「模板不正确」并给出模板下载入口。
2. 无表头文件不得丢行：整行匹配列名才判定为表头；单行文件同样可导入。
3. 行级校验逐行返回结果，异常行给出「行号 + 字段 + 原因」，不因单行失败中断整批。
4. 导入结果页展示：总行数、成功行数、失败行数、失败明细下载。
5. 同一文件重复导入不产生重复数据（按判重键幂等）。

### 9.6 校验提示要求

1. 表单校验错误提示定位到具体字段并说明原因，禁止只提示「参数错误」。
2. 提交类操作一次性列出全部缺失项，不只报第一个。
3. 拦截类提示必须说明「为什么不行 + 怎么改」，例如「第 2 行满减金额 15 元不得大于等于门槛 10 元」。
4. 危险操作（终止、删除、覆盖导入）二次确认，确认文案写明后果。

### 10.2 接口通用约束

1. **鉴权**：AccessToken + 签名（时间戳 + 随机串 + 业务参数），时间戳偏差超过 5 分钟拒绝，防重放。
2. **幂等**：所有写接口必须支持请求号幂等；资金与核销类接口必须有业务主键幂等（批次号 + 订单号、文件指纹 + 账期）。
3. **重试**：调用方失败重试间隔递增，最多 3 次；平台侧保证重试不产生重复数据。
4. **限流**：按应用维度限流，超限返回明确错误码与重试建议（具体阈值待压测确定）。
5. **错误码**：区分参数错误、鉴权失败、业务拒绝、系统异常四类，返回可读原因与唯一请求号便于排查。
6. **版本**：接口路径带版本号，向后兼容；破坏性变更须提前通知并提供并行期。

### 10.3 后台任务

| 任务 | 频率 | 幂等策略 | 失败处理 |
| --- | --- | --- | --- |
| 外部状态与审批状态同步 | 每 10 分钟 | 按外部单号 + 状态版本 | 失败重试 3 次后告警，不影响主流程 |
| 指标计算与报表生成 | 每日 T+1 凌晨 | 按账期覆盖重算 | 重算可重跑，历史结果留痕 |
| 台账更新与自动对账 | 每日 T+1 | 按账期 + 批次 | 差异挂起，人工确认后重跑 |
| 账单数据入库及检查 | 收到账单即触发 + 每日兜底 | 文件指纹 | 校验失败不入库并告警 |
| 通知与运行维护 | 事件触发 + 每日巡检 | 消息号 | 失败重试并记录 |

### 10.5 数据口径

| 指标 | 定义 | 口径说明 |
| --- | --- | --- |
| 核销订单数 | 核销回调去重后的订单笔数 | 去重键：批次号 + 订单号 |
| 优惠金额 | 券成本合计 = Σ（批次已核销单数 × 券面额） | 不等于实际财务支出，不含平台服务费 |
| 销售额 | 核销订单实付金额合计 | 以回流订单数据为准，非估算 |
| 笔单价 | 销售额 ÷ 核销订单数 | 订单数为 0 时显示「—」，不显示 0 或无穷 |
| ROI | 销售额 ÷ 优惠金额 | 优惠金额为 0 时显示「—」 |
| 核销率 | 核销单数 ÷ 发放数量 | 发放数量以批次推送数据为准 |
| 销售额占比 | 该层级销售额 ÷ 上层总销售额 | 各层级之和允许因四舍五入与总数相差 0.01 |

> 统计时点：看板展示至 T-1；「今日」实时数据不在一期范围。

### 10.6 预算占用与对账口径（资金专项）

**预算占用规则**

1. 计划预算 = 券面额 × 发放总上限；项目占用 = Σ 计划预算。
2. 推送服务商前校验项目占用 ≤ 项目核销预算，超限拦截并提示差额。
3. 项目终止时释放未核销部分的预算额度，已核销部分不回滚。
4. 批次修改发放上限导致占用变化的，须重新校验并通过后才允许再次推送。

**对账规则（三件套不可裁剪）**

| 要素 | 要求 |
| --- | --- |
| 幂等 | 核销事件按「批次号 + 订单号」去重；账单按「文件指纹 + 账期」去重；发券按「会员 + 批次 + 请求号」去重 |
| 对账 | 每日 T+1 比对三方数据：平台台账、服务商账单、小程序核销事件；输出差异清单（多记 / 少记 / 金额不符），差异挂起待人工确认，不自动冲销 |
| 资损监控 | 五类告警：单批次核销金额超预算、重复核销单、面额与批次不符、负金额或零金额核销、账单差异率超阈值（建议 0.5%，待确认） |

> 一期不含资金划付与结算单，对账目标是「数据一致」，不是「资金清算」。

### 10.7 日志与埋点

1. 系统日志记录六类关键动作（提交、审批、推送、确认、回传、终止）及所有主数据变更。
2. 日志字段：时间、操作人、角色、模块、操作、对象编号、说明、结果、来源 IP、请求号。
3. 业务埋点仅保留系统内可采集的事件（页面访问、按钮点击量如需统计，由前端日志承载），不接第三方分析平台（见 N-03）。

## 十三、验收标准与验收方法

### 13.1 验收依据与判定原则

1. **唯一依据**：本文档第八章功能需求、第九章字段规则、第十一章非功能需求。原型仅用于说明交互，不作为验收依据。
2. **判定原则**：以「按文档操作能否得到文档描述的结果」为判定标准，不以「感觉好不好用」判定。
3. **证据要求**：每条验收结论须有截图、日志或数据记录作为支撑，口头确认不构成验收通过。
4. **口径优先**：文档与原型冲突时以本文档为准；文档未覆盖的细节，由双方在验收会上确认并补入文档后判定。

### 13.2 验收通过标准

| 项 | 标准 |
| --- | --- |
| P0 功能 | 100% 通过，不允许带缺陷通过 |
| P1 功能 | ≥95% 通过，未通过项须有明确修复计划与时间 |
| 缺陷等级 | 致命 / 严重缺陷为 0；一般缺陷 ≤5 且不影响主流程；轻微缺陷记录后修复 |
| 数据一致性 | 计划与批次一一对应，核销数据与台账一致，对账差异可解释 |
| 稳定性 | 连续 3 个工作日无新增致命 / 严重缺陷 |
| 文档交付 | 部署说明、操作手册、接口文档、测试报告齐全 |

**缺陷等级定义**

| 等级 | 定义 | 示例 |
| --- | --- | --- |

### 13.5 验收不通过的处理

1. 单项不通过：记录问题编号与现象，我方在整改期内修复并回归，回归通过后该项转「通过」。
2. 整机不通过：致命或严重缺陷超过标准，或 P0 通过率低于 100%，验收整体不通过，双方重新约定整改与复验时间。
3. 争议项：以本文档条款为准；文档未覆盖的，由双方产品负责人当场确认并补入文档，作为后续判定依据。
