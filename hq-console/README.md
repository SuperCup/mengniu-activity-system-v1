# 蒙牛活动管理平台 · 一期总部端（多文件工程版）

原始交付物是一个 373 KB / 3,899 行的单文件 HTML（`蒙牛活动管理平台_一期总部端UI_V5.html`）。
本项目把它拆成一个**正常的多文件前端工程**，按《蒙牛 MTL 平台视觉规范》重做视觉
（说明：MTL 只是那份 UI 规范的出处，**系统名称就叫「蒙牛活动管理平台」**），
并把《20261020_蒙牛券中台一期_客户待确认事项清单_v4》中标黄的功能点一并落地。

---

## 一、怎么运行

不依赖构建工具、不依赖本地服务器，**双击即可打开**：

1. 双击 `login.html` → 钉钉扫码登录页（示例页）→ 点「模拟扫码成功」或「暂不登录，直接进入」
2. 或直接双击 `index.html`（未登录会先跳到登录页；地址后加 `?nologin=1` 可跳过）
3. 左侧菜单切换模块；地址栏支持 `#v-manage`、`#v-plan` 这类直达锚点

> 之所以保持「无构建 + 经典 script 标签」，是因为原型要在现场用 `file://` 双击打开：
> ES Module 与 `fetch` 拉取片段在 `file://` 下会被浏览器拦截。

### 拆分方式（为什么是这个形状）

- **单入口 SPA**：所有页面模板在启动时一次性挂到 `#viewRoot`，靠 `.view` / `.view.on` 显隐切换。
  这样保留了原单文件里跨模块的 `getElementById` 联动（例如项目审批与项目管理共用同一份项目数据），
  又避免了片段加载。
- **一个模块一个文件**：模板写成返回字符串的函数，注册到 `MT.definePage({ id, title, crumb, group, template })`；
  抽屉走 `MT.defineDrawer(id, template)`。逻辑函数与模板放在同一文件。
- **数据与视图分离**：`js/data/*` 只有数据，改一条数据不需要动任何模块。
- **样式只在 tokens 里定义颜色**：页面 CSS 不出现硬编码色值，全部引用 `var(--brand)` 这类变量。

## 六、数据说明

- 全部为演示数据，集中在 `js/data/*`，改字段值即可看到页面联动。
- 项目状态：`draft / pending / approved / confirmed / running / stopped`，定义在 `data/projects.js` 的 `PROJ_STATES`；
  新增状态只需改这一处，列表、卡片动作、顶部筛选、详情时间线会一起生效。
- 计划与批次是**强 1:1**：`PLANS[*].bat` 为空表示「待补充批次」；`PLANS[*].proj` 决定它归属哪个项目，
  「计划与批次」按项目进入时即按此过滤。
- 二维码、批次、看板数字都由同一份计划数据派生，不存在两处口径。

## 七、和原始单文件版本的关系

- 页面结构、交互与文案尽量保持原样，改动集中在：拆分、视觉规范、评审意见（第四节）与标黄点（第五节）。
- 原单文件保留不动，可作为回退参考。
- 已知取舍（原型阶段）：
  - 下载类动作（导出、下载二维码、模板）只做提示，不真正生成文件；
  - 登录页为示例页，未接钉钉真实扫码接口（对接文档未提供）；
  - 项目卡片上的动作按钮只推进状态提示，不做真实表单提交。

## 九、本轮对照实施提示词的落地内容

**流程与状态**

- 报批 → 审批 → 补配置 → 推送 已是真实动作：`submitProject` / `projApprove` / `projAct` 分别委托 `wfSubmit` / `wfApprove` / `wfAct`（`js/core/workflow.js`），会改写 `PROJECTS` / `PLANS`、冻结审批快照并重绘所有列表。
- 提交条件包含 PO 校验结果：PO 不存在或未审批直接拒绝提交。
- 审批通过后进入「待补配置」，同一 `planId` 继续补执行配置，不复制计划。
- 推送前置校验：本项目下所有计划必须「校验通过」，否则列名阻止推送。

**执行配置（`js/components/config-drawer.js` + `js/core/readiness.js`）**

- 顶部固定展示审批通过时的方案快照（只读），下方分「基础与优惠规则 / 商户及商品 / 参与领取限制 / 展示与说明 / 校验与服务商交接」五组。
- 字段按活动类型（全场代金券 / 定额立减 / 随机立减 / 全场折扣）动态显示，切换类型不会把旧类型字段算作已填。
- 允许不完整时「保存草稿」；「配置完成」要求全部必填与业务规则通过，缺失项可点击跳到对应字段。
- 未核验的微信条件单独提示「微信创建条件：待核验 N 项」，不阻断推送服务商。

**入口联动**

- 工作台新增「待我补充执行配置」待办，点击直接定位到原计划配置抽屉。
- 项目管理里已批准/已确认项目显示「待补配置 x/y」标签，主按钮改为「继续完善计划」。
- 计划表新增「配置状态」列（待完善 / 完善中 / 校验通过）与「继续配置」入口。
- 支持可恢复路由：`#v-plan?projectId=..&planId=..&tab=config`，刷新后仍定位同一计划。

**数据与持久化（`js/core/store.js`）**

- localStorage 单键存储，带 `schemaVersion` 与迁移；首次进入才写入种子数据，之后刷新保留本地记录。
- 解析失败或写入失败不覆盖原数据，会提示并保持内存草稿。
- 「系统管理」提供「重置演示数据」，需确认后执行，不在启动时重置。

5. **邮件与外部创建**：推送服务商只写本地交接记录，不发真实邮件，也不调用微信接口。
6. **微信字段核验**：见 `docs/微信执行字段待核验.md`，未核验项不阻断推送，但也不会显示「已具备微信创建条件」。

## 十一、批次计划与计划补充

**术语：一个批次等于一张券。** 一个计划对应一个批次（便于管理），一个项目（活动）下会有多个计划，也就是多个批次。

创建项目第四项「批次计划」逐行填写：

| 列 | 说明 |
| --- | --- |
| 计划名称 | 内部管理用的计划叫法，如「双节满减主推」 |
| 券名称 | 这个批次在微信后台的券名称，如「双节常温奶满减券」 |
| 机制 | 只写优惠口径，如「满 99 减 15」 |
| 发券方式 | 领券 / 过机立减 |
| 活动零售商 | 多项，点「明细 N」逐行维护或按模板导入 |
| 活动商品 | 多项，点「明细 N」逐行维护或按模板导入 |

审批通过后进入「补充执行配置」，同一抽屉顶部列出本项目所有计划/批次，点标签即可切换，逐个补齐；配置页不填归属商户号，由服务商配券时补充。

审批、项目列表、项目详情、计划与批次页统一使用同一套字段：批次计划 / 券名称 / 机制 / 发券方式 / 活动零售商 / 活动商品。

**其他修复**：浏览器限制本地存储时，不再每次刷新在底部弹红色提示框，改为页面顶部一条可关闭的中性提示条。

## 十二、日期与审批列表

**日期格式**：所有有效期、活动周期、批次可用时间、领券页有效期统一为 YYYY-MM-DD（如 2026-12-28 ~ 2027-01-05），不再出现 12-28 这类省略年份的写法。统一走 mnDate()（js/core/format.js），兼容 2026/12/28、2026年12月28日 等输入。数据看板趋势图的横轴刻度属于图表标签，仍是 12-20 形式。

**审批列表**：

1. 卡片直接复用项目管理的 projCard()，字段与项目管理完全一致：创建业务部门 / 投放平台 / 预算来源 / 核销预算 / 活动周期 / 服务商 / 机制 / PO 单号，右侧显示项目单号，底部显示最近保存时间。
2. 顶部不放状态页签，改为筛选条件：审批状态（待审批 / 已通过 / 已终止 / 全部，默认「待审批」）+ 关键字（项目名称 / 项目单号 / 提报人），配查询与重置。
3. 每页 15 条，底部有总数与分页。
4. 只有「待审批」的卡片出现驳回 / 同意按钮，其他状态只保留查看详情。

## 十三、补充执行配置的入口与页面信息

1. 项目管理里「继续完善计划」不再直接弹出配置抽屉，而是进入该项目的「计划与批次」页；点某个计划后的「补充配置」才打开配置页。
2. 「计划与批次」页顶部直接展示创建项目的三项内容：一、基本信息（项目名称 / 项目目标 / 投放平台 / 活动周期 / 活动负责人 / 联系方式）；二、预算与费用科目（PO 单号 / 核销预算 / 费用科目 / 承担主体 / 预算来源）；三、服务商信息（服务商 / 对接联系人 / 邮箱）。不再单独放置「项目详情」按钮。
3. 配置页顶部只保留该计划/批次的方案快照（券名称 / 发券方式 / 机制 / 活动周期 / 计划预算），不再显示所属项目等重复信息。

## 十四、补充配置 = 批次信息页

1. 计划与批次列表里，每个计划后的「补充配置」直接打开「补充批次信息」页（对齐微信支付后台批次字段：券名称、券面额、使用门槛、可用开始/结束时间、发放总上限、单人可领个数、使用说明，右侧带卡包预览）。已填过的显示「修改批次」。
2. 原来那套「补充执行配置」抽屉（五个分组、微信必填标签、商户授权核验）已整体删除，不再出现在任何入口。
3. 「配置状态」「待补配置 ready/total」「推送服务商前的校验」统一改为读批次信息表单：没填 = 待完善，填了但缺项 = 完善中，齐全 = 校验通过。已有批次号的历史计划已按批次字段回填一份表单，显示校验通过。
4. 项目管理「继续完善计划」仍然只跳到该项目的计划与批次页，由用户挑计划点「补充配置」。
5. 只有计划状态为「待完善」（还没有批次号）时，计划行与计划详情里才有「补充配置」入口；待配置、进行中、已结束、已中止的计划只保留「明细」。

## 十五、补充配置页的明细

「补充批次信息」页在券字段之外，补上两块与创建计划一致的明细：

1. 三、活动零售商明细：零售商名称 / 门店名称 / 省份 / 城市 / 微信商户号，支持「按模板导入零售商门店名单」（导入抽屉与创建计划共用，导完自动回到本页），可逐行移除，未填商户号的条目提示"推送服务商后由服务商提报时补充"。
2. 四、活动商品明细：69码或店内码 / 商品名称 / 店内码所属零售商，支持「按模板导入商品明细」。
3. 保存时要求零售商明细与商品明细各至少 1 条；保存后写回计划的 retRows / skuRows，计划详情抽屉同步显示这两张明细表。

## 十六、系统日志

新增「系统日志」页（左侧「配置」分组，地址 #v-log），只读记录关键操作：

1. 列：时间（精确到秒）/ 操作人（含角色）/ 模块 / 操作 / 对象（含编号）/ 说明 / 结果 / 来源 IP。
2. 筛选：模块、结果（成功/失败）、时间范围（年月日）、关键字（操作人 / 对象 / 说明），每页 15 条，按时间倒序。
3. 记录来源：项目提交审批、撤回、推送服务商、重发、终止、删除草稿、复制项目、审批通过/驳回、创建与编辑计划、保存批次配置（含明细条数）。写入统一走 sysLog()（js/core/audit.js），最多保留 500 条。
4. 日志随项目、计划一起进本地仓库（store schema 5），刷新不丢；「导出当前结果」在本机生成 CSV。
5. 种子日志 30 条，时间对齐演示时点（2026-10 上旬至 10-21）。
